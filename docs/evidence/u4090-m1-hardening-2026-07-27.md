# u4090 M1 lifecycle-hardening evidence - 2026-07-27

## Scope

This evidence supplements `u4090-m1-2026-07-27.md` for GitHub issue #5. It does not replace or relax the limitations of the original M1 proof.

The hardened slice adds:

- provider capability filtering and route-labelled diagnostics;
- separate bounds for TCP, SSH, daemon commands, proxy startup, WebSocket upgrade, app-server requests, turn-notification inactivity, and reconnect inspection;
- active resource closure when blocked socket, SSH, proxy, or WebSocket work is cancelled;
- truthful one-shot Dealer states and UI/notification cancellation;
- one user card reconciled through pending, accepted, delivered, or unknown delivery.

Concrete endpoints, credentials, host-key material, thread IDs, prompts, and client IDs are omitted because this repository is public.

## Automated checks

Focused tests exercised unsupported-route skipping, ordered fallback, actionable error preservation, route-labelled terminal SSH host-key failures, phase timeouts, reconnect timeout, cancellation while awaiting `turn/start`, cancellation during blocked WebSocket input, and cancellation of an actual blocked loopback socket read.

Fixture tests verified monotonic `LOCAL_PENDING` -> `ACCEPTED` -> `DELIVERED` revisions, completed-turn recovery, `UNKNOWN` delivery when acceptance could not be established, and no replay of `turn/start`.

Dealer unit tests verified that normal and recovered one-shot runs end in non-running `COMPLETED` and `RECOVERED` states, that active-route display follows connection phase, and that service-owned terminal state remains available after rebinding. Android lint and assembly verified the foreground-service notification cancel action and Dealer UI cancel path.

The final Gradle 9.5.1 command ran `test`, `lint`, and `:apps:dealer:assembleDebug` with rerun tasks and the build cache disabled. All 94 actionable tasks executed successfully.

## Live u4090 checks

The official upstream Codex `0.145.0` daemon remained running on u4090.

The normal opt-in LAN test repeated the complete M1 path through real TCP, pinned-host-key SSH, daemon query, proxy WebSocket, initialization, thread list/resume/read, streamed turn completion, and fresh reconnect. It confirmed one matching user message, a delivered user card, and only LAN attempts from the LAN-only provider.

A second opt-in test deliberately closed the first app-server connection immediately after the successful `turn/start` response. A counter wrapping every initial and reconnect app-server peer confirmed that the client issued `turn/start` exactly once; reconnect found exactly one matching authoritative user message and upgraded the same local card to `DELIVERED`.

## Limits

- Dealer UI and notification cancellation were compiled, unit-tested, and linted but were not exercised on Fold6 hardware.
- The controlled interruption closed the client connection; it did not kill the daemon process or workstation network interface.
- Embedded `tsnet`, external-Tailscale routing, DERP, third-party VPN coexistence, battery behavior, and Fold6 lifecycle remain M1T validation work.
- This evidence covers upstream Codex `0.145.0` only and does not claim broad version compatibility.
