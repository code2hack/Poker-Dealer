# Fold6 Termux M2T turn evidence — 2026-07-28

## Scope

This records the first real-device M2T capability slice for GitHub issue #13: Fold6 Termux as an
opportunistic phone-local Codex host reached only through loopback SSH and the shared
daemon-backed app-server stack. It proves lifecycle qualification, local-TUI coexistence, and one
Dealer turn. It does not prove Android suspension recovery or mark the Termux host fully
supported; that recovery work remains issue #14.

Thread IDs, client-generated message IDs, process IDs, private-key material, host-key material,
and concrete private-network endpoints are omitted.

- Device: Samsung SM-F956N (Fold6), Android 16, Samsung build
  `BP4A.251205.006/F956NKSS4DZG1`.
- Termux: `0.118.3`, Android ARM64 (`aarch64`).
- Community distribution: `@mmmbuto/codex-cli-termux`.

- Dealer: debug APK SHA-256
  `ba38d5e17f2f4d955f69f89760800410efef578bd6cb7e7f87fba51f4221cf86`.

The canonical host catalog classifies this host as `TERMUX_ANDROID`, `ANDROID_ARM64`,
`TERMUX_COMMUNITY`, and `OPPORTUNISTIC`, with exactly one route: `SSH_LOOPBACK`.

## Trust boundary and route

A dedicated RSA-3072 Dealer key was authorized in Termux. Dealer used the Android-compatible PEM
serialization of that key, strict host-key checking, and a separately reviewed pinned
`known_hosts` file. Password fallback was disabled in the independent live-stack check. The key
and pins remained outside the repository with the private key at mode `0600`.

The installed Dealer APK imported both files through Android's document picker and kept their
bytes only in process memory. The exact temporary private-key, public-key, and pin-file copies
were removed from Fold6 shared storage immediately after import and verified absent. No
credential or thread identity was written to Room, DataStore, repository files, or application
logs. Dealer did not persist the lifecycle socket path; its observed value appears only in the
two non-secret compatibility fixtures.

Dealer connected to the Termux SSH listener at Android loopback. It did not use LAN, embedded
tsnet, external Tailscale, ADB tunneling as a product route, or direct access to Termux-private
files or Unix sockets. Wireless ADB and a host-side ADB port forward were used only to drive and
observe the development test.

## Distribution-specific daemon lifecycle

The community build was exercised through its own machine-readable lifecycle commands:

1. with no daemon socket, `codex app-server daemon version` exited nonzero and reported the
   missing control socket;
2. `codex app-server daemon start` returned JSON with status `started`, PID backend, managed
   community Codex path/version, control-socket path, CLI version, and app-server version;
3. the following version query returned JSON status `running` with the same version and socket
   fields; and
4. `codex app-server proxy` upgraded to WebSocket and carried the app-server session.

The observed start and running payload shapes are committed as compatibility fixtures, with the
ephemeral numeric process ID normalized to `0`. The Termux adapter accepts only the observed
`started` start status, then requires explicit `running` status and a nonblank reported control
socket. It does not invoke the upstream Linux installer, updater, or bootstrap behavior.

## Shared-stack capability check

The opt-in `TermuxLiveM2TTest` used pinned SSH over loopback and the production
route-neutral TCP, SSH, proxy WebSocket, app-server, projection, delivery-reconciliation, and
reconnect layers. Against the real Fold6 it verified:

1. one `initialize`/`initialized` exchange on each app-server connection;
2. thread listing, resume, read, and turn start through stable methods;
3. existing-history projection and streamed committed output;
4. a fresh SSH, proxy, WebSocket, and initialized app-server connection after the turn;
5. exactly one matching submitted user message after authoritative reread;
6. the user card reaching `DELIVERED`; and
7. all attempted route diagnostics remaining `SSH_LOOPBACK`; and
8. safe rejection of one live unsupported server-initiated request.

For the last check, a separate harmless live probe set the stable turn-level approval policy to
`untrusted` and asked for exactly one non-writing shell command. The tested app-server sent one
`item/commandExecution/requestApproval` request. Dealer's production WebSocket peer returned its
explicit JSON-RPC rejection, the server unblocked, and the turn completed with the expected
committed marker response. The test restored the thread's `never` approval policy and verified
the returned setting. No approval was granted.

Fixture tests retain unknown optional daemon fields and continue to cover arbitrary unknown
notifications, item types, and server-request method names without parsing unsupported payloads.

## Installed Dealer APK turn

On the Fold6, Dealer selected the canonical Fold6 Termux host, accepted only an explicit loopback
SSH port, and hid workstation and embedded-tailnet controls. Dealer claimed soft control for the
exact host-qualified thread before enabling send.

The APK then submitted one reviewed marker prompt. The live UI showed:

- `Running | SSH_LOOPBACK`;
- only `SSH_LOOPBACK: selected` in route diagnostics;
- app-server `0.145.0`;
- the one current user card moving from local pending to accepted and finally
  `COMMITTED | DELIVERED`;
- streamed agent output with the exact requested marker in terminal `COMMITTED` state; and
- terminal run state `Completed`.

After the required fresh reconnect and thread reread, the projection contained one copy of the
current prompt and response. The earlier OpenSSH private-key serialization was rejected locally
as `invalid privatekey` before SSH; reimporting the same authorized RSA key in PEM serialization
completed the run. The rejected attempt did not reach Termux and its local pending card was
replaced rather than duplicated by the successful run.

## Local-TUI coexistence and control

The Termux-local TUI used the same community distribution's `codex --remote unix://...` launcher
against the daemon's reported control socket. Dealer explicitly yielded its indicator from
`Control: DEALER` to `Control: LOCAL_TUI` after completion. The already-open local TUI displayed
the exact Dealer APK prompt and response in the same thread without daemon restart, thread
migration, or a second backend.

This is the specification's soft human-control indicator, not a distributed lock.

## Compatibility disposition and limits

Fold6 Termux remains **DEGRADED**, not `SUPPORTED`, until issue #14 proves interruption and Android
suspension recovery without replay. This evidence covers one Fold6, one Termux package, one
community distribution/version, one local-TUI thread, and one successful APK turn. It does not
qualify install/update behavior, other community builds, Android process suspension, broad
version skew, or Poker behavior.
